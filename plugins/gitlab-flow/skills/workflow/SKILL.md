# GitLab Flow 提交规范

## ⚠️ 绝对安全红线（严格禁止）

- **明确分支定义**：在本规范中，"**个人分支/工作分支**"指的是 **除 `main` 和 `production` 以外的任何/所有分支**（例如你新创建的特性分支、修复分支等）。
- **禁止错误合并（双重红线）**：
  1. **绝对禁止将 `main` 分支合并到你的个人/工作分支中！**
  2. **绝对禁止将 `main` 分支合并到 `production` 分支中！**
- **原因背书**：`main` 分支可能包含其他协同人员提交的、未经完整生产测试的功能。如果将 `main` 合并回个人/工作分支，或者将 `main` 直接合并到 `production`，都会导致这些未经测试的功能在随后的步骤中被错误地一同带入 `production`（生产环境），从而造成生产事故。
- **冲突处理（交互规范）**：
  - 如果个人/工作分支与目标分支存在冲突，**立即暂停操作**。
  - 向用户清晰报告：**① 为什么会产生冲突（具体冲突的文件和原因）**，**② 你的修改/解决建议是什么（如保留哪方代码、如何合并代码逻辑等）**。
  - **必须等待用户明确同意你的修改建议后**，方可着手解决冲突。

## 操作前检查

- 检查当前分支和工作区改动，确认 `main` 和 `production` 均存在。检查远程分支时，区分本地远程跟踪引用和实时远程状态。
- 任一指定分支不存在或无法确认时，向用户明确报告缺少或无法确认的具体分支并暂停，等待用户决定；不得自行创建缺失分支或改用其他分支。
- 创建、切换或删除分支，暂存、提交、合并、推送及其他改变 Git 状态的操作，均须事先得到用户明确授权；本规范本身不构成授权。只处理用户授权的改动，保留其他本地改动。

## 提交流程

1. 基于 `production` 创建并检出新的工作分支。
2. 在新分支上提交用户授权的本地改动。
3. 将新分支合并到 `main`。合并成功后保留新分支，不要删除。
4. 暂停并等待用户在 `main` 合并完成后明确确认；不得以前面的授权代替此次确认。
5. 收到确认后，**将该新分支直接合并到 `production`**，绝对不得将 `main` 合并到 `production`。
6. 仅在合并到 `production` 成功后删除该新分支，然后重新检出 `main`。删除远程分支须获得用户对远程删除或推送的明确授权。

## 异常与失败处理

- 如果出现冲突、切换分支会覆盖本地改动、或任何操作失败，立即暂停并报告。
- 不得强制合并（不要使用 `--force` 或 `-f`）、不得强制删除分支、不得丢弃用户改动。
